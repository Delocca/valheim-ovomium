# Ovomium — mod Valheim (BepInEx 5 + Harmony, C#)

Voir `README.md` pour les fonctionnalités et options. Ce fichier : ce qu'un agent doit savoir pour travailler ici.

## Environnement

- Jeu : `~/.local/share/Steam/steamapps/common/Valheim`, Valheim **1.0.15** (patch du 2026-09-19 ; décompilé régénéré, tous les ancrages revérifiés OK), Unity 6, Mono, Linux natif. BepInExPack_Valheim 5.4.2350 installé (`tools/install-bepinex.sh`). Journal : `BepInEx/LogOutput.log` (lisible).
- Aucun outil .NET sur l'hôte : tout passe par l'image podman `ovomiam-build` (`tools/Containerfile`). `Ovomium.sln` = quatre projets, propriétés communes dans `Directory.Build.props` : le cœur du mod (`Ovomium/` → `Ovomium.Core.dll`, version dans son csproj), le chargeur (`Ovomium.Loader/` → `Ovomium.dll`, voir plus bas), le patcher BepInEx `Ovomium.Updater/` (version fixe 1.0.0, déployé dans `BepInEx/patchers/`, pris en compte à la relance ; il ne peut pas se mettre à jour lui-même) et `Ovomium.Tests/` (net8.0, logique pure sans Unity/Valheim compilée par lien, ex. `StackGrouping.cs` ; exécuté par le build, un test en échec fait échouer le build). Le patcher n'a pas d'`Unload` ni de hot reload : le tester exige une relance.
- `tools/build.sh` et `tools/deploy.sh` sont **exclus du bac à sable** (`.claude/settings.json`) : les lancer **exactement** sous la forme `tools/build.sh Release` depuis le dépôt (répertoire de travail de la session ; un argument obligatoire, rien d'autre dans la commande : ni `cd … &&`, ni `| tail`, ni `2>&1`, sinon podman échoue dans le bac à sable : depuis Claude Code 2.1.277, chaque partie d'une commande composée doit matcher `excludedCommands`, et `allowUnsandboxedCommands: false` interdit toute autre sortie). Toute autre commande podman ou accès à nuget/mcr/thunderstore échoue dans le bac à sable.
- **Chargeur et cœur** : `Ovomium.Loader/` → `Ovomium.dll` (version fixe 1.0.0, seul plugin BepInEx, GUID `ovo.ovomium`) démarre `Ovomium/` → `Ovomium.Core.dll` depuis ses octets, renommée par Cecil (`Ovomium.Core-<ticks>`, sinon Unity confond les MonoBehaviour de deux versions), et la remplace à chaud de façon **synchrone** (`Plugin.Unload` complet + destruction immédiate de l'objet hôte, puis `Plugin.Load` de la nouvelle ; échec → ancienne redémarrée depuis ses octets gardés). Contrat par réflexion, à garder compatible dans les deux sens (le chargeur n'est remplacé qu'à la relance) : `public static void Ovomium.Plugin.Load(GameObject host, ManualLogSource log, Action<string> requestReload)` et `Unload()`. Résultat publié dans l'AppDomain : `Ovomium.Loader.CorePath`, `Ovomium.Loader.LastError`. Chaque chargement : nouveau `ConfigFile` sur `ovo.ovomium.cfg` (les abonnements `SettingChanged` de l'ancienne version restent sur l'ancien, inerte) et identifiant Harmony = nom de l'assembly. Guetteurs (`MonoBehaviour`) : sur l'objet hôte passé à `Load`, jamais sur un objet persistant.
- **Déploiement possible jeu lancé** : `deploy.sh` remplace chaque fichier par renommage atomique (`.new` puis `mv -f`) ; le chargeur reste mappé par Mono (qui lit les méthodes à la demande : le réécrire en place casserait les patches pas encore exécutés, `BadImageFormatException: Method has zero rva`), le nouveau sert au prochain lancement ; le cœur est lu depuis ses octets, jamais verrouillé. Après un build, lancer `tools/deploy.sh --relaunch Release` en arrière-plan (`run_in_background`) : il copie, attend la fermeture du jeu par Edia, puis le relance via Steam avec `-ovomium-autojoin`. Les tests en jeu sont faits par Edia ; comparer son retour avec les traces `… trié :` du journal (option `LogSortOrder = true` dans `BepInEx/config/ovo.ovomium.cfg`, désactivée par défaut).
- **Rechargement à chaud** (par le chargeur ; ScriptEngine retiré le 2026-09-25) : `tools/deploy.sh --dev Release` pose le marqueur `BepInEx/plugins/Ovomium/dev-reload` ; le chargeur sonde la date d'`Ovomium.Core.dll` chaque seconde et recharge au changement (F6 en secours), en partie comprise, journal `Mode dev : rechargement…`, `… déchargé` puis `… chargé`. `Plugin.Unload` appelle le `Unload()` de chaque feature à effets de scène (FirstPerson, LoadingArt, SettingsMenu, PasswordReveal, MinimapSize, ServerWake, Updater, etc.) puis `UnpatchSelf` ; **toute feature neuve à effets de scène doit y figurer** : c'est aussi le chemin des mises à jour chez les amies (au menu). Ce qui tourne avant le menu principal, le chargeur et le patcher exigent une relance. `deploy.sh` sans `--dev` retire le marqueur (mode normal, pas de relance nécessaire).

## Règles de code

- **Une fonctionnalité = un dossier** `Ovomium/Features/<Nom>/` avec `<Nom>Config.cs` (ConfigEntry, section du même nom) et `<Nom>Patch.cs`. Le partagé métier va dans `Ovomium/Food/`. `Plugin.cs` ne fait que binder les configs et `PatchAll`.
- Patches Harmony **toujours avec types d'arguments explicites** (`typeof(...)` ou `new System.Type[0]`) : la 1.0 a ajouté des surcharges, un patch ambigu fait échouer tout le plugin au chargement.
- Dans une classe de patch, `Prepare`, `Cleanup`, `TargetMethod(s)` sont des noms réservés par Harmony : un helper ainsi nommé est appelé par Harmony avec d'autres arguments et fait échouer le patch.
- `Console` du jeu masque `System.Console` : ne pas importer `System` dans les patches qui l'utilisent.
- Warnings = erreurs (`TreatWarningsAsErrors`). Version du mod : `<Version>` du csproj uniquement (cible `GeneratePluginVersion` → `PluginVersion.Value`).
- Autocontrôle au chargement (`PatchInstaller`) : patches posés classe par classe puis JIT forcé de toutes les méthodes du mod ; le journal conclut par `Autocontrôle OK : N classes de patch posées, M méthodes compilées` ou une erreur par ancrage manquant (la feature concernée est perdue, les autres tournent). Après une mise à jour du jeu, lire cette ligne avant toute autre vérification.
- Journal : `Plugin.Log`. Traces de tri en `LogInfo` derrière `LogSortOrder` ; le niveau Debug n'est pas écrit dans `LogOutput.log` par défaut.
